# 2026-11-22 10:32 — 本地模型试验：路由 + 读日志，2B 对 9B

## 背景
用户提出：把**模型路由**（决定用哪一档云端模型，避免中途切换）和**用户发起的长文本读取**（日志等）交给本地模型，并要求把 2B 和 7B 级的都实测一遍给结论。

## 做了什么
- 新增离线评测 `os/model/bench/router_bench.py`（llama-cpp-python，语法约束输出，非思考模式）。
- 新增数据：`os/model/ci/router_v1.jsonl`（90 条，每档 30，中英各约半）、`router_v2_heldout.jsonl`（**全新**的 60 条留出集，每档 20）。
- 新增测试 `os/verify/test_router_bench.py`（10 项，不需要模型）：数据集形状/不重叠、日志生成器种子固定、**根因行压缩后必须保留**、grep 基线只在“不误导”的日志上命中、尾部基线永不命中。
- 原始结果存档：`os/model/bench/results/2026-11-22/`。

## 方法（读结果前请先看）
- 模型：`unsloth/Qwen3.5-2B-GGUF` 与 `unsloth/Qwen3.5-9B-GGUF`，同为 **Q4_K_M**。9B 是 Qwen3.5 家族里最接近 7–8B 的一档，**没有测 Qwen3-8B 或其他厂家**。
- 机器：4 核 Xeon CPU、15 GB 内存、**没有显卡**；上下文 4096、4 线程。所以延迟只反映 CPU，不能当作宿主显卡的数据。
- **标签是我按档位定义写的**，没有第二个人复核；数字代表“与这套定义一致的程度”，不是客观真值。
- 任务 A（路由）：local / flash / pro 三选一。**少判（该 pro 判成 flash/local，或该 flash 判成 local）才是代价高的错误**，多判只多花钱。
- 任务 B（读日志）：先用**确定性**步骤压缩（相同模板合并、保留首次行号和次数、超预算时优先保留稀有行），再让模型给出最多 4 个根因行号。日志是合成的、种子固定：6 种场景 × 2（好抓/误导）。“误导”指：根因行没有 error 关键词，且前面放了 6 条无害的 error 诱饵；这是我**故意设计**的，所以另外单独报告。
- 同时给出两个纯规则基线：grep 错误关键词、取末尾几条。

## 结果

### 路由
| 评测 | 提示词 | 2B 准确率 | 9B 准确率 | 2B 少判 | 9B 少判 |
|---|---|---|---|---|---|
| v1（90） | A（初版定义） | 74.4% | 71.1% | 17.8% | 28.9% |
| 留出（60） | A | 70.0% | 80.0% | 5.0% | 20.0% |
| 留出（60） | **B（有判定顺序）** | **90.0%** | **96.7%** | 6.7% | 3.3% |

- 两个模型在 v1 上都栽在 **flash 档**（2B：16 条判成 local；9B：26 条判成 local）。local 和 pro 两端几乎满分。**这说明问题在档位定义含糊，不在模型大小**。
- 提示词 B 把定义改成“先看是否需要深推理 → 再看是否写/改/解释代码 → 否则才是 local”。B 是**看了 v1 错题后写的**，所以只能在没参与调参的留出集上评价；留出集上 B 对 A：2B 70→90%，9B 80→96.7%。
- 2B 在 A 下的错法在 v1 和留出集上**完全不同**（前者 flash→local，后者 flash→pro 15 次），说明它在中间档上不稳定；B 下仍有 6 个错，其中一个是 **pro 被判成 local**（“缓存命中率在周末凌晨掉到零”）。
- 9B 在 B 下只错 2 条，都是**中文**的疑难诊断（“O(n²) 退化”“O2 错 O0 对”）被判成 flash，英文 100%。
- 中位延迟（CPU）：2B 约 2.7 s，9B 约 9.4 s。

### 读日志（12 条，压缩后约 160 条/约 2200 token）
| | 全部 | grep 友好（6） | grep 误导（6） | 中位耗时（CPU） |
|---|---|---|---|---|
| 9B 命中 | **12/12** | 6/6 | **6/6** | 约 91 s |
| 9B 第一条即根因 | 10/12 | 6/6 | 4/6 | |
| 2B 命中 | 8/12 | 6/6 | **2/6** | 约 21 s |
| grep 基线 | 6/12 | 6/6 | 0/6 | 瞬时 |
| 取末尾基线 | 0/12 | 0/6 | 0/6 | 瞬时 |
- 压缩后根因行 12/12 保留，所以失败都是模型选错，不是被压缩丢了。
- 9B 的 91 s 是 CPU 上处理约 2200 token 提示词的耗时，**不代表显卡**；显卡数据本轮没有，不下结论。

## 结论
1. **路由：能交给本地，但要带判定顺序的提示词（B）。** 2B 常驻可用（90%），9B 更稳（96.7%）。因为少判才是贵的错误，必须配套：规则优先；有疑问向上判；失败自动升档；界面显示“选了哪档、为什么”并可一键改。2B 单独用时 6.7% 的少判（含 pro 判成 local）不能无兜底地放行。
2. **读日志：2B 不够，9B 级才可靠。** 对比 grep：好抓的日志 grep 就够了；根因藏起来时 grep 全灭、2B 勉强（2/6）、9B 全中（6/6）。所以模型的价值只在“grep 看不见”的那类日志，前提是**先做确定性压缩**。
3. **建议分层**：guest 的 2B 常驻只做路由；有宿主显卡时由 7–9B 做日志筛选；没有显卡时日志走“确定性压缩 + 规则筛选 + 原文行号展示”，不要强行让 2B 概括。
4. 数据规模小（路由 60/90 条、日志 12 条、单次、温度 0），差异在 3–4 条之内的（比如 90% 对 96.7%）**不能当作显著差异**。

## 已知问题 / 局限
- 标签由我定义；留出集是我在看过 v1 错题**之后**写的，风格可能偏向提示词 B。
- 日志是合成的，格式比真实日志规整；真实日志（多行堆栈、二进制、超长行）没测。
- 只测了 Qwen3.5 的两个尺寸；没有 Qwen3-8B、没有显卡延迟、没有微调后的 2B。
- 没有把结果接进产品：规划器/路由器仍是旧逻辑，本轮**没有改默认值、没有改运行时代码**。
